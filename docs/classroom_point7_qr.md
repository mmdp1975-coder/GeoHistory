# Classroom Point 7 QR

## 1. Purpose

- This document describes the Point 7 owner-side QR support for Classroom access.
- The scope is limited to rendering the QR from the existing classroom access link and downloading the QR for owner use.
- It does not implement student join flow, invite acceptance, membership creation, actual email sending, WhatsApp sharing, journey assignment, or analytics.

## 2. Files changed

- `frontend/app/module/classroom/[id]/page_inner.tsx`
- `frontend/app/module/classroom/qr.ts`
- `frontend/app/module/classroom/utils.ts`
- `docs/classroom_point7_qr.md`

## 3. How QR invite rows are created/reused

- The owner Classroom detail page derives the QR from the current classroom access invite.
- Reuse rule:
  - if an active `invite_type = 'link'` row exists, the page reuses it as the primary access token
  - if a legacy active access row exists, the page can still reuse it for compatibility
  - if no active access row exists, the owner creates the classroom access link first
- The QR section no longer creates a separate QR-specific invite row by default.
- The token continues to be generated by the existing database schema on `classroom_invites.token`.

## 4. How QR rendering works

- QR rendering is local to the frontend and does not use an external QR service.
- The QR value is the same classroom access link format already used in Point 6.
- The page builds the QR value from the primary access token and passes it to a local helper:
  - `buildClassroomInviteLink(token)`
  - `renderQrSvg(link, options)`
- The QR helper generates SVG markup from the link and the page renders it inline for visual verification.

## 5. How QR download works

- The owner can download the QR as PNG.
- The page:
  - builds an SVG data URL from the same invite link
  - loads it into an `Image`
  - draws it onto a canvas
  - exports the canvas with `toDataURL("image/png")`
  - triggers a browser download
- This keeps the download local to the browser and does not require server-side image generation.

## 6. Access control behavior

- Only the classroom owner can access the Classroom detail page and therefore the QR section.
- Invite rows remain protected by the existing Point 4 RLS policies on `classroom_invites`.
- Non-owners continue to receive the existing controlled unavailable/access-denied state.
- QR data is not exposed publicly.

## 7. What is intentionally deferred to Point 8 and later

- Student join flow
- Invite acceptance or membership creation
- QR consumption logic
- Actual email delivery
- WhatsApp sharing logic
- Journey assignment
- Progress, quiz, ranking, or analytics

## 8. Acceptance criteria for Point 7

Point 7 is complete when:

- The owner can create or reuse the classroom access token used for link sharing.
- The owner can see a rendered QR code for the same invite link.
- The QR encodes the same invite link used in Point 6.
- The owner can download the QR as PNG.
- The owner can deactivate the active classroom access token.
- Non-owners cannot manage the QR section.
- No student join flow is implemented.
- No invite acceptance or membership logic is implemented.
- `docs/classroom_point7_qr.md` exists.
