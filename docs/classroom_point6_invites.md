# Classroom Point 6 Invites

## 1. Purpose

- This document describes the Point 6 owner-side invite management flow.
- The scope is limited to creating, listing, and deactivating invite rows for a classroom owned by the current user.
- It does not implement QR rendering, student join/acceptance, actual email sending, WhatsApp sharing, members management, journey assignment, or analytics.

## 2. Files changed

- `frontend/app/module/classroom/[id]/page_inner.tsx`
- `frontend/app/module/classroom/types.ts`
- `frontend/app/module/classroom/utils.ts`
- `docs/classroom_point6_invites.md`

## 3. Invite creation flow

- Invite management is embedded in the existing owner Classroom detail page.
- The owner creates or reuses one classroom access invite.
- The frontend now creates only the token-based access row needed for the classroom link:
  - `classroom_id`
  - `invite_type = link`
- The token is not generated in frontend code.
- The token is generated by the database through the existing schema default on `classroom_invites.token`.
- After insert, the UI reads back the created row and adds it to the owner access-link list.
- Email is not treated as a separate invite flow in the owner UI. It is only a future distribution channel for the same generated link.

## 4. Invite listing behavior

- The owner detail page loads existing access-related `classroom_invites` rows for the current classroom.
- The list shows:
  - primary or legacy access status
  - active/inactive status
  - created date
  - raw token
  - derived invite link
- Email-target management is no longer exposed in the owner UI.
- Invite rows are loaded only after the classroom has already been confirmed as owner-accessible.

## 5. Revoke/deactivate behavior

- Invite management uses reversible deactivation instead of physical deletion.
- Deactivation updates `classroom_invites.active` from `true` to `false`.
- Inactive invite rows remain visible to the owner in the list.
- Active rows show a `Deactivate` action.

## 6. How invite links are built

- Invite links are built in the Classroom UI from the stored token.
- The helper uses:
  - current `window.location.origin` when available
  - a stable token query parameter
- The current derived link format is:
  - `/module/classroom/invite?token=<token>`
- The same link is the only owner-facing access artifact.
- QR generation and future email or WhatsApp sharing must reuse this exact link.

## 7. Access control behavior

- Only the classroom owner can read or manage `classroom_invites` rows through the existing Point 4 RLS policies.
- The owner detail page remains owner-only.
- Non-owners continue to receive the existing controlled unavailable/access-denied state.
- Invite rows are not exposed publicly.

## 8. What is intentionally deferred to Point 7 and later

- QR rendering or QR download behavior
- Student join flow
- Invite acceptance / membership activation logic
- Actual email delivery
- WhatsApp sharing logic
- Journey assignment
- Progress, quiz, ranking, or analytics

## 9. Acceptance criteria for Point 6

Point 6 is complete when:

- The owner can create an invite row for their classroom.
- A unique invite token is generated by the existing database schema.
- The owner can see the list of invite rows for their classroom.
- The owner can see a shareable invite link derived from the token.
- The owner can deactivate an existing invite.
- Non-owners cannot manage invites.
- No QR rendering or QR generation is implemented.
- No student join or invite-acceptance flow is implemented.
- No actual email sending is implemented.
- `docs/classroom_point6_invites.md` exists.
